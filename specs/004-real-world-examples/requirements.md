# Requirements

## Goal
Provide executable, privacy-safe examples that let developers see Context Guard inventory, guarded-profile, quality, and token-measurement workflows for Claude Code and Codex, including representative output and a path to run against their own local logs.

## Problem Statement
The v0.1.0 commands are documented individually, but developers cannot yet run one coherent end-to-end demonstration or see what safe output looks like. This makes the value difficult to evaluate and encourages ad hoc access to sensitive local logs.

## Scope
In scope:
- A checked-in examples directory with deterministic demo inputs for Claude and Codex.
- An executable demo runner that uses an isolated temporary HOME and never mutates the real HOME.
- Captured, stable, privacy-safe example output generated by the runner.
- A documentation page explaining sandbox demo and opt-in real-local commands.
- README and MkDocs navigation links.

Out of scope:
- Publishing raw local session logs, prompts, responses, absolute home paths, or secrets.
- Claiming a universal 30 percent reduction without 5x3 qualified evidence.
- Automatically launching Claude Code or Codex.

## Actors
- Developer evaluating Context Guard before installation.
- Maintainer regenerating and verifying examples.
- Security reviewer confirming that published evidence is sanitized.

## Inputs
- Checked-in synthetic skill manifests and provider usage event fixtures.
- Explicit user-selected Claude JSONL or Codex JSONL paths for real-local runs.
- The current Context Guard CLI.

## Outputs
- `examples/run_demo.py` executable demo runner.
- `examples/fixtures/` deterministic provider fixtures.
- `examples/output/demo-output.json` sanitized generated evidence.
- `docs/real-world-examples.md` with commands and interpretation.

## Functional Requirements
- FR-001: The demo MUST run without reading or writing the caller's real HOME.
- FR-002: The demo MUST exercise both Claude and Codex inventory/profile-related behavior and provider-native token extraction where supported by deterministic fixtures.
- FR-003: Generated output MUST contain only relative example identifiers, counts, digests, statuses, and token totals.
- FR-004: A maintainer MUST be able to regenerate checked-in output with one documented command.
- FR-005: Documentation MUST provide opt-in commands for explicit real-local log paths and explain required quality authorization.
- FR-006: Documentation MUST distinguish illustrative fixture results, local measured results, and qualified 30 percent claims.
- FR-007: The demo MUST fail non-zero on command failure or output drift.

## Non-Functional Requirements
- NFR-001: Python 3.10+ and no new runtime dependency.
- NFR-002: Deterministic output across machines after volatile paths and timestamps are excluded.
- NFR-003: No network access.
- NFR-004: No secret, prompt, response, raw log, or absolute HOME path in checked-in output.
- NFR-005: Demo runtime target under 10 seconds.

## Constraints
The existing CLI quality-authorization boundary remains authoritative. Examples may demonstrate extraction with valid generated authorization fixtures, but must not weaken or bypass production checks.

## Acceptance Criteria
- AC-001: Running `python3 examples/run_demo.py --check` succeeds from a clean checkout and verifies checked-in output.
- AC-002: The demo touches only a temporary directory and repository example output when explicitly regenerating.
- AC-003: Output includes Claude cache creation/read tokens and Codex cached input tokens from deterministic fixtures.
- AC-004: Output includes inventory/profile decisions for both providers without absolute user paths.
- AC-005: The docs show explicit commands for real Claude and Codex logs and warn that raw logs remain local.
- AC-006: A repository test detects output drift and privacy-forbidden keys/patterns.
- AC-007: README and MkDocs expose the examples page.

## Out of Scope
- Publishing raw local logs, prompts, responses, or absolute user paths.
- Automatically running provider sessions.
- Marketing claims based only on deterministic fixtures.

## Assumptions
- The first examples optimize for evaluation and reproducibility, not automatic provider launch.
- Real-local commands require the developer to select log files explicitly.
- Checked-in numbers are fixture measurements and are labeled as such.

## Open Questions
None blocking. Future work may publish a separately consented, qualified 5x3 benchmark dataset.

## Decision Status
All blocking decisions are resolved. Accepted assumption: public evidence uses deterministic fixtures while real-local evidence is opt-in through explicit user-selected paths. Recorded as DEC-001.
